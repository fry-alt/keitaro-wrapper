# Keitaro wrapper

Обёртка над рекламным трекером [Keitaro](https://keitaro.io):

1. **Создатель кампаний.** Принимает название, страны и оффер. Создаёт в Keitaro кампанию с двумя потоками: первый отправляет всех из выбранных стран на Google, второй отправляет остальных на оффер. У кампании выставлены домен, группа и источник.
2. **Редактор существующей кампании.** Добавляет и удаляет офферы в потоках, пересчитывает доли трафика и закрепляет доли. Изменения копятся в черновике и уходят в Keitaro по кнопке Push.

**Развёрнуто:** https://keitaro-wrapper.vercel.app (вход по паролю, пароль выдаёт автор).

Стек: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL или SQLite, HTMX и Tom Select на фронте. Работает локально, в Docker и на Vercel.

Всё проверено на настоящем трекере `tlgk.host`: живой тест создаёт кампанию, правит офферы, публикует, ловит правку из админки и удаляет кампанию (см. [Тесты](#тесты)).

## Быстрый старт

Нужен Python 3.12+.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env        # впишите KEITARO_API_KEY и свой CAMPAIGN_PREFIX
alembic upgrade head        # создаст базу (по умолчанию SQLite в data/app.db)
uvicorn app.main:app --reload
```

Откройте http://localhost:8000.

### Без доступа к Keitaro (демо)

```bash
KEITARO_FAKE=1 uvicorn app.main:app --reload
```

Вместо трекера работает Keitaro в памяти с тестовой кампанией и офферами. Весь интерфейс работает, настоящий Keitaro не трогается.

### В Docker (с PostgreSQL)

```bash
cp .env.example .env        # впишите ключ и префикс
docker compose up --build
```

Приложение поднимется на http://localhost:8000, миграции применятся при старте.

## Миграции

Схема базы ведётся через Alembic, база задаётся переменной `DATABASE_URL`.

| Что сделать | Команда |
|---|---|
| Применить все миграции | `alembic upgrade head` |
| Откатить последнюю | `alembic downgrade -1` |
| Текущая версия базы | `alembic current` |
| Проверить, что модели совпадают с миграциями | `alembic check` |
| Создать миграцию после изменения `app/models.py` | `alembic revision --autogenerate -m "что изменилось"` |

Сгенерированную миграцию нужно просмотреть в `migrations/versions/` перед применением. Тест `tests/test_migrations.py` гоняет `upgrade → check → downgrade → upgrade` на SQLite, а CI повторяет то же самое на PostgreSQL.

Примеры `DATABASE_URL`:

```
sqlite:///./data/app.db
postgresql+psycopg://app:app@localhost:5432/keitaro_wrapper
```

## Настройки (`.env`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `KEITARO_URL` | `https://tlgk.host` | адрес трекера без `/admin` |
| `KEITARO_API_KEY` | — | ключ Admin API (в админке: Maintenance → Users → API Keys) |
| `CAMPAIGN_PREFIX` | `test_` | префикс имени кампании, например `test_ivanov_`. Править можно только кампании с ним |
| `DEFAULT_DOMAIN` | `kylovoa.com` | домен новых кампаний |
| `DEFAULT_GROUP` | `FORTESTS` | группа новых кампаний |
| `DEFAULT_TRAFFIC_SOURCE` | `FORTESTS` | источник новых кампаний |
| `REDIRECT_URL` | `https://google.com` | куда первый поток отправляет трафик из выбранных стран |
| `DATABASE_URL` | `sqlite:///./data/app.db` | база приложения |
| `OFFERS_CACHE_TTL` | `600` | через сколько секунд обновлять локальный каталог офферов |
| `APP_PASSWORD` | — | пароль входа. Пустой — вход не нужен (локально). На Vercel обязателен |
| `SECRET_KEY` | — | ключ подписи cookie; пустой — выводится из пароля |
| `EDIT_ANY_CAMPAIGN` | `0` | `1` — разрешить правку кампаний без префикса |
| `KEITARO_FAKE` | `0` | демо-режим без настоящего Keitaro |

Домен, группа и источник задаются названиями, их ID приложение находит в Keitaro само.

## Как это работает

### Создание кампании

Форма: **Name**, **Geo** (одна или несколько стран), **Offer** (поиск по ID и названию). Что происходит:

1. Проверяется всё, что можно проверить до обращения к Keitaro: имя, коды стран (ISO 3166), существование оффера, наличие домена, группы и источника. При ошибке в Keitaro ничего не создаётся.
2. Создаётся кампания (`POST /campaigns`) с ротацией потоков «по позиции», доменом, группой и источником. К имени добавляется префикс `test_фамилия_`, если его нет.
3. Создаётся поток 1 (`POST /streams`): фильтр «страна = выбранные», действие: редирект на `REDIRECT_URL`.
4. Создаётся поток 2: без фильтров, оффер со share 100%. Потоки проверяются по порядку, поэтому сюда попадают все, кого не поймал первый.
5. Если поток не создался, кампания удаляется, чтобы в Keitaro не оставался полуфабрикат.
6. Кампания сразу подтягивается в базу и открывается в редакторе.

То же доступно через JSON API: `POST /api/campaigns`, документация на `/docs`.

### Редактор

Повторяет логику из видео:

| Действие | Что происходит |
|---|---|
| **Fetch streams from KT** | Подтягивает потоки кампании. Потоки без офферов показываются только названием, их содержимое не разбирается. |
| **Add** | Оффер добавляется, доли пересчитываются, поток становится жёлтым («не опубликовано»). В Keitaro пока ничего не меняется. |
| **Push to KT** | Отправляет черновик потока в Keitaro. |
| **Cancel** | Отменяет неопубликованные правки: добавленные офферы удаляются, остальные возвращаются к опубликованным долям. |
| **Remove** | Оффер становится серым с долей 0%. После Push он пропадает из Keitaro, но остаётся у нас в архиве. |
| **Bring back** | Возвращает удалённый оффер. |
| **📌 / клик по доле** | Закрепляет долю: текущую или введённую вручную. Закреплённые доли не меняются при пересчётах. |
| Оффер удалили прямо в Keitaro | После Fetch он не пропадает, а становится removed (серый, с Bring back). |

Изменённые доли показываются вместе с прежним значением («было 33%»), новые офферы подсвечены зелёным, внизу таблицы — сумма долей.

### Модель данных: черновик и опубликованное

У каждого оффера в потоке (`stream_offers`) два состояния:

- `published_active` / `published_share` — что сейчас лежит в Keitaro (`NULL` = оффер ещё не публиковался);
- `draft_active` / `draft_share` / `pinned` — что видит и правит пользователь.

На этом построены все правила:

- поток жёлтый, если черновик хоть одного оффера отличается от опубликованного;
- **Push**: опубликованное = черновик;
- **Cancel**: черновик = опубликованное, а записи, которых в Keitaro не было, удаляются;
- **Fetch**: опубликованное = данные Keitaro (Keitaro — источник правды).

Остальные таблицы: `campaigns`, `streams` и `offers` (локальная копия каталога офферов). У `GET /offers` в Keitaro нет поиска, поэтому каталог скачивается целиком и автодополнение ищет по своей базе. Копия обновляется, если старше `OFFERS_CACHE_TTL`.

Права в Keitaro устроены так, что часть офферов API-ключу не видна: `GET /offers/{id}` отвечает 403, но в поток такой оффер ставится. Поэтому в поиске можно ввести ID любого оффера. При добавлении приложение спрашивает Keitaro напрямую: 403 значит «оффер есть, название скрыто» (он показывается как «Оффер #ID»), 404 значит «оффера нет», и добавление отклоняется.

### Расчёт долей

`app/services/shares.py`, чистая функция без базы и сети:

- закреплённые доли не меняются;
- остаток `100 − сумма закреплённых` делится поровну между незакреплёнными;
- доли целые (Keitaro принимает только целые). Лишние проценты получают первые по порядку добавления: 3 оффера → **34 / 33 / 33**, 25% закреплено + 2 оффера → **25 / 38 / 37**;
- закрепить больше 100% в сумме нельзя: правка отклоняется, данные не меняются;
- если закреплены все офферы и сумма не равна 100%, Push блокируется с объяснением.

Свойства алгоритма проверяются property-тестами (Hypothesis) на случайных наборах: сумма всегда 100, закреплённые не тронуты, незакреплённые отличаются максимум на 1.

### Что выяснилось на настоящем Keitaro

Документация Admin API описывает часть полей неполно, поэтому всё сверено с живым трекером:

- фильтр страны: `{"name": "country", "mode": "accept", "payload": ["AU", "MX"]}`; редирект: `schema: "redirect"`, `action_type: "http"`, адрес в `action_payload`;
- `PUT /streams/{id}` с полем `offers` **заменяет список офферов целиком**: так и работает Push;
- Keitaro **молча принимает** несуществующий `offer_id` и сумму долей 120%. Поэтому приложение само проверяет, что оффер существует, а сумма равна ровно 100%;
- ключу видна только часть офферов: `GET /offers/{id}` у остальных отвечает 403, но в поток они ставятся. Такие офферы добавляются по ID и показываются как «Оффер #ID, название скрыто»;
- у кампании в ответе есть поле `domain` с полным адресом (`https://kylovoa.com/`), из него строится ссылка для трафика.

### Защита от потери данных

- **Конфликты.** Перед Push поток перечитывается из Keitaro и сравнивается с тем, что мы видели при последней синхронизации. Если кто-то поменял поток в админке, Push отменяется с просьбой сделать Fetch, и чужие правки не затираются.
- **Проверка результата.** После Push сверяется, что Keitaro сохранил ровно то, что мы отправили.
- **Fetch с черновиками.** Если есть неопубликованные изменения, интерфейс сначала спрашивает подтверждение.
- **Повторы запросов.** При сетевых сбоях и ответах 502/503/504 повторяются только идемпотентные запросы (GET/PUT/DELETE). POST не повторяется, чтобы не создать кампанию дважды.
- **Дубли.** Один оффер нельзя добавить в поток дважды. Если он среди удалённых, интерфейс подскажет вернуть его через Bring back.

### Безопасность

Приложение управляет общим трекером, поэтому в интернете его нельзя оставлять открытым:

- **Вход по паролю** (`APP_PASSWORD`). Сессия хранится в подписанной HMAC cookie: `HttpOnly`, `SameSite=Lax`, `Secure` за HTTPS, живёт 7 дней. Пароль сравнивается за постоянное время, после неверного ввода стоит пауза в 1 с против перебора. JSON API принимает `Authorization: Bearer <APP_PASSWORD>`. На Vercel без пароля приложение отвечает 503 и не работает открытым.
- **CSRF.** Изменяющие запросы с чужого сайта отклоняются по заголовкам `Origin` и `Sec-Fetch-Site`, а cookie не уходит в кросс-сайтовые POST-запросы (`SameSite=Lax`).
- **Заголовки.** Строгий CSP (`script-src 'self'`, без inline-скриптов и стилей), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, HSTS, `Cache-Control: no-store` для страниц. htmx и Tom Select лежат в `app/static/vendor`, а не грузятся с CDN; `eval` в htmx выключен.
- **XSS.** Jinja экранирует всё, что пришло из Keitaro (названия офферов и кампаний); в автодополнении текст тоже экранируется. Есть тест с `<script>` в названии оффера.
- **Чужие кампании.** Трекер общий с другими людьми, поэтому править можно только кампании с `CAMPAIGN_PREFIX`. Остальные открываются для просмотра, кнопок правки у них нет, а сервер отклоняет такие запросы.
- **Без открытых редиректов.** После входа переход разрешён только на свои пути.
- **Секреты** (`.env`, ключ API, пароль) в репозиторий не попадают; на Vercel они лежат в Environment Variables.
- **Проверено:** `pip-audit` (известных уязвимостей в зависимостях нет), `bandit` (единственное замечание низкой важности: флаг `secure` у cookie вычисляется по протоколу, так и задумано), `tests/test_security.py`.

## Деплой на Vercel

Vercel запускает FastAPI как serverless-функцию: точка входа — `index.py` в корне. Нужна внешняя PostgreSQL: файловая SQLite на serverless не сохраняется. Подойдёт Neon из Vercel Marketplace.

1. Создайте проект и подключите базу: `vercel link`, затем `vercel integration add neon`. Можно и вручную задать `DATABASE_URL`: адрес вида `postgres://…` приложение само переводит на драйвер psycopg.
2. Задайте переменные окружения: `KEITARO_API_KEY`, `CAMPAIGN_PREFIX`, `APP_PASSWORD`, `SECRET_KEY` (`vercel env add …`).
3. Примените миграции к этой базе со своей машины: `DATABASE_URL=<адрес из Vercel> alembic upgrade head`.
4. Выложите: `vercel deploy --prod`.
5. Проверьте: `curl https://<проект>.vercel.app/healthz?deep=1` должен вернуть `{"status":"ok","db":"ok","keitaro":"ok"}`. Глубокая проверка публичная, но отдаёт только ok/fail и кэшируется на минуту.

Зависимости для Vercel закреплены в `requirements.txt`. На serverless соединения с базой не держатся в пуле (`NullPool`).

## Структура

```
app/
  main.py               # FastAPI-приложение
  security.py           # вход, CSRF, заголовки безопасности
  web.py                # HTML-страницы и HTMX-действия редактора
  api.py                # JSON API (/api/offers, /api/campaigns)
  config.py             # настройки из .env
  db.py, models.py      # SQLAlchemy
  keitaro/
    client.py           # HTTP-клиент Admin API: ошибки, повторы
    schemas.py          # модели ответов Keitaro
    fake.py             # Keitaro в памяти: тесты и демо-режим
  services/
    shares.py           # расчёт долей
    editor.py           # add / remove / bring back / pin / push / cancel
    sync.py             # Fetch: сверка с Keitaro
    creator.py          # создание кампании
    offers.py           # локальный каталог офферов и поиск
    countries.py        # справочник стран ISO 3166
  templates/, static/   # интерфейс
index.py                # точка входа для Vercel
migrations/             # Alembic
tests/
```

## Тесты

```bash
pytest            # всё, кроме обращений к настоящему Keitaro
pytest -m live    # полный цикл на настоящем Keitaro (нужны ключ и префикс в .env)
ruff check . && ruff format --check .
```

- `test_shares.py` — расчёт долей, включая property-тесты;
- `test_editor.py` — все сценарии редактора из видео на Keitaro в памяти;
- `test_creator.py` — создание кампании, проверки ввода, откат при сбое;
- `test_client.py` — HTTP-клиент: заголовок ключа, повторы, тексты ошибок;
- `test_web.py` — страницы, HTMX-действия и JSON API через HTTP;
- `test_security.py` — вход, cookie, CSRF, заголовки, запрет правки чужих кампаний, экранирование;
- `test_migrations.py` — миграции применяются, откатываются и совпадают с моделями;
- `test_live.py` — живой тест на настоящем Keitaro. Создаёт кампанию со своим префиксом и закрытым оффером, проходит Add → Push → Pin → Remove → правка в админке → конфликт при Push → Fetch, сверяет каждое состояние через API и удаляет кампанию.

CI (GitHub Actions) запускает линтер и тесты, а также прогоняет миграции на PostgreSQL.
